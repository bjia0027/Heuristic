## 📋 优化概述

### 问题描述
当前调度算法对节点的任务并发没有严格的容量限制，导致：
- ❌ **无容量限制**: 任何可用节点都可以接受新任务
- ❌ **无排队建模**: 没有考虑节点任务队列长度
- ❌ **忽略饱和状态**: 高负载节点仍然被选择
- ❌ **过载风险**: 可能导致单个节点CPU饱和、内存I/O争用

### 优化目标
在HEFT调度算法中增加容量约束机制，避免单节点承担过多任务。

### 修改3: 修复容量约束判断逻辑

**文件**: `core/dag_heuristic_scheduler_optimized.py`  
**行数**: 2447-2454

**修改前**:
```python
# 🆕 容量约束：如果负载过高且有其他选择，跳过该节点
if load_ratio > MAX_LOAD_RATIO and len(candidates) > 0:
    self.logger.debug(f"跳过过载节点 {machine_id}: load_ratio={load_ratio:.2f} > {MAX_LOAD_RATIO}")
    continue
```

**修改后**:
```python
# 🆕 容量约束：如果负载过高且有其他可用机器，跳过该过载节点
# 这可以避免单个节点承担过多任务，防止CPU饱和、内存I/O争用
if load_ratio > MAX_LOAD_RATIO and available_machines_count > 1:
    self.logger.debug(f"⚠️ 跳过过载节点 {machine_id}: "
                    f"当前负载={current_load}, 平均负载={avg_load:.1f}, "
                    f"负载比={load_ratio:.2f} > {MAX_LOAD_RATIO} "
                    f"(可用机器数={available_machines_count})")
    continue
```

**关键改进**:
1. ✅ **修复逻辑错误**: 
   - 旧逻辑 `len(candidates) > 0`：判断是否已经有候选机器（在遍历过程中逐步累积）
   - 新逻辑 `available_machines_count > 1`：判断总共有多少可用机器
   - **问题**：旧逻辑会导致第一个机器永远不会被跳过（因为此时 candidates 还是空的）

2. ✅ **增强日志输出**: 提供更详细的调试信息，包括当前负载、平均负载、负载比、可用机器数

## 💡 关键技术点

### 1. 容量约束机制
```python
# 计算负载比率
current_load = sum(1 for e in schedule if e.machine_id == machine_id)
load_ratio = current_load / avg_load if avg_load > 0 else 0

# 容量约束判断
if load_ratio > MAX_LOAD_RATIO and available_machines_count > 1:
    # 跳过过载节点
    continue
```

### 2. 参数配置
- **LOAD_BALANCE_THRESHOLD = 1.3**: 超过平均负载130%时启用惩罚
- **LOAD_PENALTY_FACTOR = 0.5**: 惩罚系数
- **MAX_LOAD_RATIO = 1.5**: 超过平均负载150%时强制跳过

### 3. 多层防护
1. **软约束**: 负载比 > 1.3 时，增加 EFT 惩罚，降低选择优先级
2. **硬约束**: 负载比 > 1.5 时，直接跳过该节点（除非唯一选择）
3. **兜底机制**: 确保至少有一个节点可以接受任务
